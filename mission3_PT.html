항목 14 MAC 점수가 높으면 왜 더 유사한가

답변필터에서 1인 자리는 "여기가 칠해져 있어야 한다"는 표시입니다. 패턴도 그 자리가 1이면 1×1=1로 점수가 붙고, 어긋나면 0을 곱해 점수가 붙지 않습니다. 따라서 겹치는 칸이 많을수록 점수가 커지고, 그만큼 모양이 비슷하다는 뜻이 됩니다.

한계도 함께 말합니다. 원시 MAC 점수는 필터의 총합 규모에 영향을 받습니다. 총합이 크게 다른 필터끼리 점수를 직접 비교하면 왜곡될 수 있고, 실제로 이 미션의 실패 3건이 그 사례입니다. 실무 CNN이 정규화를 쓰는 이유가 여기 있습니다.

def mac(pattern, filter_data):
    score = 0.0                # 점수통 비우기
    for row in range(len(pattern)):        # 행
        for col in range(len(pattern[row])):  # 열
            score += pattern[row][col] * filter_data[row][col]
    return score

이 다섯 줄이 담은 것

입력패턴과 필터 두 장을 인자로 받음

파일 표기 → 프로그램의 표준어

파일 표기어디에표준 라벨

대소문자와 앞뒤 공백은 미리 정리한 뒤 비교하므로 "Cross", " X " 같은 표기도 인식됩니다.

함수 하나로 분리한 이유

def normalize_label(raw):
    text = str(raw).strip().lower()
    if text == "+" or text == "cross":
        return "Cross"
    elif text == "x":
        return "X"
    else:
        return None   # 모르는 라벨

표기가 늘어나도 이 함수만 고치면 됩니다. 판정·출력·집계 코드는 표준 라벨만 다루므로 영향받지 않습니다.

항목 5·12 · 구역 [3] 분리의 장점과 확장 절차

장점. 표기 해석 규칙이 한 곳에 모여 있어 변경 지점이 하나입니다. 해석 불가는 None 으로 돌려주므로 잘못된 라벨을 조용히 통과시키지 않고 해당 케이스만 실패로 기록합니다.

순서단계위치
1정규화 — 새 표기를 표준 라벨로 매핑[3]
2판정 — 두 점수 비교를 최댓값 비교로 확장, 1등과 2등 차이가 EPSILON 미만이면 동점[2]
3출력 — 고정된 두 줄을 라벨별 반복 출력으로 변경[8]
4테스트 — 해당 라벨의 필터와 케이스를 추가해 결과 확인data.json

08핵심 원리 · 부동소수점

0.1 + 0.2 는 0.3 이 아닙니다항목 16·17

컴퓨터는 0.1을 2진수로 정확히 표현하지 못합니다. 그래서 같은 값이라도 더하는 순서에 따라 소수점 아래 끝자리가 갈립니다.

>>> 0.1 + 0.2
0.30000000000000004

이 어긋남이 점수 비교에 그대로 들어옵니다. 실제 실행에서도 수학적으로 같은 값이 이렇게 나왔습니다.

Cross 점수: 0.9
X 점수:     0.8999999999999999
차이: 1.11e-16

허용오차로 동점을 선언합니다

EPSILON = 1e-9

if abs(score_a - score_b) < EPSILON:
    return "UNDECIDED"

부등호만으로 비교하면 오차가 승부를 결정합니다. 1e-9보다 작은 차이는 실력 차이가 아니라 계산 순서의 잔여물이므로 동점으로 봅니다.

실측 오차는 1e-16 ~ 1e-15 수준이고, 의미 있는 점수 차이는 0.1 이상이었습니다. 1e-9는 그 사이에서 양쪽과 충분히 떨어진 값입니다.

답변규칙 자체를 다르게 둔 것이 아니라 요구사항이 다릅니다. 모드 1은 사람과 대화하는 입력 모드라 채점 대상이 없으므로 한글로 판정 불가를 안내하고 끝냅니다. 모드 2는 expected 와 대조하는 채점 모드이므로 표준 표기인 UNDECIDED 로 남기고, 정답과 일치할 수 없으니 실패로 집계합니다. 판정 함수는 하나이고 전달하는 라벨 문자열만 다릅니다.

증상이다. epsilon을 없애도 실패 수는 줄지 않습니다. 다만 epsilon 덕분에 우연한 오판정이 진단 가능한 신고로 바뀝니다.

데이터 문제인가

그렇다. 근본 원인이다. 필터 값을 직접 합산해 확인했습니다. 아래 표를 보십시오.

필터 값을 직접 더해 확인한 것

크기성립하는 관계값동점 케이스
5×5Cross 필터 중앙 한 칸 = X 필터 전체 합0.9 = 0.9size_5_1
13×13X 필터 중앙 한 칸 = Cross 필터 전체 합7.5 = 7.5size_13_2
25×25Cross 필터 중앙 한 칸 = X 필터 전체 합4.9 = 4.9size_25_1

Cross 패턴과 X 패턴은 정중앙 한 칸에서만 겹칩니다. 그래서 정답 필터의 점수(전체 합)와 오답 필터의 점수(중앙 한 칸)가 수학적으로 같아집니다. 크기마다 이 관계가 한 방향씩만 성립하므로 각 크기당 정확히 1건씩, 총 3건이 동점이 됩니다.

항목 9 이 분석이 향하는 결론

답변실패 3건은 구현 오류가 아니라 데이터에 설계된 동점 상황이며, 프로그램은 이를 임의로 판정하지 않고 정직하게 신고하고 있습니다. 교훈은 총합 규모가 다른 필터끼리 원시 MAC 점수를 직접 비교하면 안 된다는 것이고, 개선한다면 필터를 정규화해 스케일을 맞추는 방향입니다. 다만 이번 미션은 주어진 데이터와 비교 정책을 그대로 따르는 것이 요구사항이므로 판정 규칙은 변경하지 않았습니다.

O(N²)의 근거

MAC은 N×N 모든 칸을 정확히 한 번씩 방문하므로 연산 횟수는 정의상 N²입니다. 13×13에서 25×25로 갈 때 연산은 3.7배, 시간은 약 3.3배 늘어 증가율이 수렴합니다.

측정 경계

스톱워치를 mac() 호출 직전과 직후에만 걸었습니다. 사용자 입력이나 파일 읽기는 사람의 속도와 디스크 속도에 좌우되므로 연산 성능이 아닙니다.

CPU와 NPU의 병목 차이

MAC은 칸끼리 서로 의존하지 않아 원래 동시에 계산해도 되는 연산입니다.

CPU복잡한 명령을 순서대로 처리하도록 설계됨. 단순 연산을 줄 세워 실행하는 직렬 큐가 병목
NPU곱셈기를 수천 개 배치해 동시에 계산. 계산은 빨라지지만 그만큼 값을 공급해야 하므로 메모리 대역폭이 병목으로 옮겨감

그래서 실제 NPU 설계는 연산기 수를 늘리는 것만큼 데이터를 재사용해 메모리 접근을 줄이는 데 집중합니다.
